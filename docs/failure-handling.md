# 장애 대응 / 백업(Fallback) 동작

이 앱은 별도 DB가 없고(서버리스 전환 시 SQLite 제거), 각 단계의 상태는 **Slack
메시지 자체**(버튼 `value`, 모달 `private_metadata`)로 운반된다. 영속 기록은
**Google Sheets가 유일**하다. 따라서 "백업"은 데이터를 어딘가에 별도 저장하는 큐가
아니라, **각 외부 호출(Slack API, Sheets API) 실패를 감지해 사람이 알아챌 수 있게
알리는 것**으로 구현되어 있다. 이 문서는 그 동작을 단계별로 정리한다.

## 처리 흐름과 각 단계의 실패 시 동작

```
① /에듀카드 제출
   → 로그 채널에 '대기중' 카드 게시 (스레드 기준점 생성)
② 승인자에게 DM 카드 전송
③ 승인자가 [승인]/[반려] 클릭
   → 승인자 DM 카드 업데이트
   → 채널 '대기중' 카드 업데이트
   → 채널 스레드에 결과 답글 게시
④ Google Sheets에 한 행 기록
```

### ① 채널 게시 실패 (`view_submission.py: process_submission`)

`chat_postMessage`(로그 채널)가 실패하면 **신청 자체가 성립하지 않은 것으로 간주**하고
그 자리에서 중단한다. 승인자 DM도 보내지 않는다. 신청자에게
"신청 접수 중 오류가 발생했습니다. 잠시 후 다시 시도해 주세요." DM을 보낸다
(`_notify_requester_error`).

- **백업 없음.** 신청 데이터는 이 시점에 메모리에만 있었고 저장된 곳이 없으므로,
  신청자가 `/에듀카드`를 **다시 제출**하는 것이 유일한 복구 방법이다.

### ② 승인자 DM 실패 (`view_submission.py: process_submission`)

채널 게시는 성공했지만 승인자 DM이 실패하면, 이미 올라간 **채널 '대기중' 카드를
`chat_delete`로 롤백**한다(승인자가 없는데 채널에 카드만 남는 상황 방지). 이후
①과 동일하게 신청자에게 재시도 안내 DM을 보낸다.

- **백업 없음.** 마찬가지로 신청자 재제출이 유일한 복구 방법.
- 롤백(`chat_delete`)마저 실패하면 예외를 로그로만 남기고(`log.exception`) 채널에
  '대기중' 카드가 고아 상태로 남을 수 있다 — 이 경우는 수동으로 채널에서 확인해
  메시지를 삭제해야 한다.

### ③ 승인/반려 처리 중 Slack 업데이트 실패 (`buttons.py: _finalize_decision`)

승인자 DM 카드 업데이트, 채널 카드 업데이트, 스레드 결과 답글 — 이 세 호출은 **각각
독립적으로 try/except로 격리**되어 있다. 하나가 실패해도 나머지는 계속 시도되고,
실패는 `log.exception`으로만 남는다(사용자에게 별도 알림 없음).

- **백업 없음, 로그만 남음.** 결정 자체(승인/반려 여부)는 다음 단계인 Sheets 기록에는
  영향을 주지 않지만, 예를 들어 채널 카드 업데이트가 실패하면 채널에는 '대기중'
  상태로 계속 보일 수 있다. 운영자가 로그를 보지 않는 한 알아챌 방법이 없다.

### ④ Google Sheets 기록 실패 (`buttons.py: _sync_sheets`) — 핵심 백업 로직

승인/반려가 확정된 직후 Sheets에 한 행을 추가한다. 이때만 **명시적인 재시도 +
사용자 노출 경고**가 있다.

```python
def _sync_sheets(sheets_sync, row, client, log_channel_id, attempts=3):
    for i in range(attempts):
        try:
            sheets_sync(row)
            return
        except Exception as e:
            last = e
            if i < attempts - 1:
                time.sleep(0.5)
    # 3회 모두 실패하면 신청 스레드에 경고 게시
    client.chat_postMessage(
        channel=log_channel_id, thread_ts=row["channel_msg_ts"],
        text=f"⚠️ Google Sheets 기록 실패 — 수동 확인이 필요합니다. (사유: {last})",
    )
```

- **재시도**: 0.5초 간격으로 최대 3회.
- **최종 실패 시**: 해당 신청의 채널 스레드에 `⚠️ Google Sheets 기록 실패 — 수동
  확인이 필요합니다. (사유: ...)` 메시지를 남긴다. 이것이 사실상의 "백업" —
  데이터를 어디 저장하는 게 아니라 **사람이 수동으로 Sheets에 넣어야 함을 알리는
  신호**다.
- **경고 게시 자체가 실패하면** 그마저도 로그(`log.exception`)에만 남고 완전히
  조용히 유실된다.

## 수동 복구 방법 (Sheets 기록 실패 시)

Sheets 행 자체는 어디에도 큐잉되지 않지만, **승인/반려가 확정된 카드에는 행 재구성에
필요한 정보가 모두 남아 있다** — 승인자 DM 카드, 채널 부모 카드(둘 다 결정 후
`build_decided_card`로 갱신됨), 스레드 결과 답글.

1. `⚠️ Google Sheets 기록 실패` 경고가 달린 스레드로 이동한다.
2. 부모 메시지(결정 카드)에서 아래 값을 확인한다: 신청자, 용도, 금액, 사용일,
   가맹점, 신청일시, 처리자, 처리일시, (반려 시) 반려 사유, (있다면) 비고.
   - 신청 고유 번호(`id`)는 메시지 알림 텍스트(`에듀카드 사용 요청 #<id> ...`)에서
     확인 가능.
3. Google Sheets에 [README 6절 "기록되는 열"](../README.md#기록되는-열) 순서(A~L)에
   맞춰 수동으로 한 행을 추가한다.
4. 경고 메시지에 수동 처리 완료를 스레드 답글로 남겨 이중 처리를 방지한다.

## 요약: 무엇이 "백업"되고 무엇이 안 되는가

| 실패 지점 | 자동 재시도 | 사용자/운영자 알림 | 데이터 유실 여부 |
|---|---|---|---|
| ① 채널 게시 | 없음 | 신청자에게 재시도 안내 DM | 유실(재제출 필요) |
| ② 승인자 DM | 없음 | 신청자에게 재시도 안내 DM + 채널 카드 롤백 | 유실(재제출 필요) |
| ③ 결정 후 Slack 업데이트 | 없음 | 없음(로그만) | 표시 불일치 가능, 결정 자체는 유효 |
| ④ Sheets 기록 | 3회(0.5s 간격) | 스레드 ⚠️ 경고 | 유실 아님 — 결정 카드에서 수동 재구성 가능 |

**결론**: 영속 재시도 큐(예: "5분마다 재시도")는 **없다**. DB를 제거한 서버리스
구조 특성상 실패 시 큐에 다시 넣을 곳이 없기 때문이다. 대신 ④에서만 즉시
재시도 + 스레드 경고로 사람이 개입하도록 설계되어 있고, ①·②는 애초에 신청자
재제출로 복구하는 것을 전제로 한다.
